## 发现的问题

### P0 - 机器损坏配置文件的核心参数未参与计算

位置：
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/services/MachineDamageService.java:97`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/services/MachineDamageService.java:558`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/config/SlimefunMachineDamageManager.java:33`

`machine-damage.yml` 暴露了 `damage_chance_scale`、`damage_chance_exponent`、`max_damage_chance`，`SlimefunMachineDamageManager` 也读取了这些配置，但 `processMachineWork()` 最终调用的是无配置参数的 `calculateDamageRate(workTicks)`。实际损坏概率由硬编码常量 `A=7.5e-6`、`B=2.5e11` 决定，服务器配置不会生效。

影响：管理员以为能调节损坏概率，实际无法调节，可能导致线上损坏率严重偏离预期。

建议：将 `MachineDamageConfig` 传入概率计算，使用 `scale * ticks^exponent` 并按 `max_damage_chance` 截断；同时在 `/sf machine-damage info` 中显示配置生效后的概率。

### P1 - 电网自调度在异步线程中读写大量非线程安全集合和 Bukkit/方块状态

位置：
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/networks/energy/EnergyNet.java:139`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/networks/energy/EnergyNet.java:145`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/networks/energy/EnergyNet.java:2352`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/networks/energy/EnergyNet.java:2379`

`scheduleSelfTick()` 使用 `runTaskTimerAsynchronously` 调用 `tickSelf()`，而 `tickSelf()` 会进入 `performEnergyTransfer()`，修改 `generators`、`capacitors`、`consumers`、`connectors`、`connectorLoad` 等 `HashMap`，并调用 `StorageCacheUtils`、`getGeneratedOutputLong()`、`setCharge()` 等涉及方块数据和物品实现的逻辑。与此同时，主线程命令、监听器和万用表显示也会读取这些集合。

影响：存在数据竞争、`ConcurrentModificationException`、读取半初始化路径、Bukkit API 异步访问异常等风险。编译无法发现这类问题。

建议：把电网状态快照和 Bukkit/方块访问分层；主线程采集/提交状态，异步线程只做纯计算；或者统一用单线程调度队列串行化所有电网状态读写。

### P1 - 长途连接器、电量计数器、限电器注册为空配方，且长途连接器损坏后无法生成修复材料

### P1 - 电量计数器缺少放置校验，与限电器互斥规则只实现了一半

- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/EnergyMeter.java:63`

- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/CurrentLimiter.java:98`

`CurrentLimiter` 放置时会校验下方是连接器，并拒绝与 `ENERGY_METER` 同格；`EnergyMeter` 放置时只记录 owner，没有校验下方连接器，也没有拒绝与限电器互斥。

建议：将两者的放置校验抽成共享方法：必须位于连接器正上方，且该位置不能已有另一种附件。

### P1 - `/sf grid` 和 `/sf machine-damage` 权限节点未在 `plugin.yml` 声明

- `src/main/java/io/github/thebusybiscuit/slimefun4/core/commands/subcommands/GridCommand.java:26`

### P1 - 修复材料重复时机器可能提前修复

位置：
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/services/MachineDamageService.java:465`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/services/MachineDamageService.java:520`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/services/MachineDamageService.java:521`

机器损坏修复材料是随机从配方抽取，可能抽到重复材料。`trySubmitRepairItem()` 按 `itemId` 累加提交数量，但 `canRepair()` 遍历修复材料列表时只检查对应 `repairId` 是否提交过一次，没有比较需要数量。若列表为 `[IRON_INGOT, IRON_INGOT]`，提交 1 个铁锭后两项都会通过。

影响：修复成本低于设计值；显示的“已提交/需要”也会误导玩家。

建议：把所需材料归并为 `(type,id) -> requiredCount`，提交材料归并为 `(type,id) -> submittedCount`，逐项比较数量。

### P2 - 限电器把禁用状态显示成无限制

位置：
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/CurrentLimiter.java:179`
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/CurrentLimiter.java:195`
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/CurrentLimiter.java:267`

聊天输入 `0` 会写入 `current-limit = "0"`，表示禁用连接器；全息也按禁用显示。但右键查看时条件 `limit == 0 && (limitStr == null || "0".equals(limitStr))` 会把 `null` 和 `"0"` 都显示为无限制，后面的禁用分支永远不会处理 `"0"`。

影响：限电器实际禁用，但玩家看到的是无限制，排障成本高。

建议：用 `limitStr == null` 表示无限制，`"0".equals(limitStr)` 表示禁用，正整数表示限额。

### P2 - 电量计数器持久值解析缺少容错

位置：
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/EnergyMeter.java:78`
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/EnergyMeter.java:108`
- `src/main/java/io/github/thebusybiscuit/slimefun4/core/networks/energy/EnergyNet.java:2341`

`energy-counter` 直接 `Long.parseLong()`，没有捕获 `NumberFormatException`。数据损坏、手动修改或旧版本遗留非数字值会导致计数器 tick 或电网自调度 tick 抛异常。

影响：单个坏数据可能中断计量更新，严重时影响电网自调度任务稳定性。

建议：封装 `parseLongOrZero()`，解析失败时清理坏值并继续运行。

### P2 - 电量计数器和限电器的显示缓存是非线程安全 `HashMap`

位置：
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/EnergyMeter.java:31`
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/CurrentLimiter.java:44`
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/EnergyMeter.java:63`
- `src/main/java/io/github/thebusybiscuit/slimefun4/implementation/items/electric/CurrentLimiter.java:76`

两种物品的 `BlockTicker` 都是异步执行，但 `displayCache` 仍然是普通 `HashMap`，同时 `onRightClick()`、`onBreak()` 和 `tick*()` 会并发读写它。

影响：在高频交互或多个区块并发更新时，可能出现缓存抖动、重复全息刷新或 `HashMap` 并发问题。

建议：改用 `ConcurrentHashMap`，或者把缓存访问也放到同一条主线程/单线程执行路径。

### P2 - 机器损坏登录提醒只覆盖已加载区块，通用方块未通知
